# ShikigamiApp ログ仕様

## 1. 目的

本書は、ShikigamiAppのGuiが出力する診断ログについて、記録内容、出力形式、保存先、出力時の動作、および障害時の取り扱いを定義する。

診断ログは、異常の発生事実だけでなく、操作開始から正常終了・失敗までの進行状況を追跡し、最後に正常完了した処理を特定できることを目的とする。

対象はGuiの診断ログであり、ScenarioRunnerの実行ログ、CoreTestのテスト結果ログ、およびPerformanceTrackerの計測値そのものは対象外とする。ただし、PerformanceLoggerの出力失敗はGuiの診断イベントとして記録する。

## 2. 基本原則

1. ユーザーにとって意味のある操作単位で記録する。個々のControlのイベント発火や御魂スロットの値設定など、細粒度の内部操作は原則として記録しない。
2. 操作の開始、正常完了、失敗を区別する。操作途中の到達地点が障害解析に重要な場合に限り、中間の完了イベントを記録する。
3. 正常完了を示すログは、そのイベントが表す処理の完了を確認してから記録する。処理の呼び出し直後や実行前に成功ログを出してはならない。
4. 診断ログ出力の失敗によって、保存・読み込み・計算・状態遷移・エラー通知等の本来の処理を中断しない。
5. ログから原因を追えるよう、イベント名と結果コードを一貫した形式で記録する。ただし、ログだけで処理が完了したことを保証するものではない。
6. 同一障害を複数の層で重複してERROR記録することは避け、利用者へ失敗を報告する処理境界で原則1回記録する。
7. ログ記録は本来の処理の成功条件としない。記録の失敗を理由に処理結果やUI状態を変更しない。

## 3. ログレベル

| レベル | 用途 | 主な対象 |
|---|---|---|
| `INFO` | 操作の開始・正常完了・主要状態変化 | 計算成功、保存成功、読み込み成功、式神復旧成功、状態遷移 |
| `WARNING` | 入力不正、想定された拒否、継続・復旧可能な事象 | Calculation入力検証失敗、式神入力検証失敗、再読み込みの自動復元開始 |
| `ERROR` | 操作の失敗、復旧不能な状態、予期しない例外 | SaveData保存失敗、ロールバック失敗、Gateway呼び出し例外 |

想定内の入力不正を`ERROR`として扱わない。正常完了した操作を`WARNING`や`ERROR`として記録しない。

## 4. 出力形式

### 4.1 レコード形式

診断ログの各イベントは以下の形式で記録する。

```text
<日時> [<レベル>] SessionId=<ID> Operation=<操作名> Event=<イベント名> [Outcome=<結果>] [補足項目]
```

例：

```text
2026-11-20 12:00:00.100 [INFO] SessionId=0123456789abcdef0123456789abcdef Operation=Calculation Event=Started ShikigamiSelected=True
2026-11-20 12:00:00.124 [INFO] SessionId=0123456789abcdef0123456789abcdef Operation=Calculation Event=Completed ShikigamiSelected=True
2026-11-20 12:01:15.200 [WARNING] SessionId=0123456789abcdef0123456789abcdef Operation=Calculation Event=ValidationRejected Outcome=INVALID_VALUE
```

上記のID・時刻・イベントは出力例であり、実際の実行結果ではない。

### 4.2 共通項目

| 項目 | 必須 | 仕様 |
|---|---|---|
| 日時 | 必須 | イベント記録時のローカル日時。書式は`yyyy-MM-dd HH:mm:ss.fff` |
| レベル | 必須 | `INFO`、`WARNING`、`ERROR` |
| `SessionId` | 必須 | アプリの起動単位で生成する一意の識別子。32桁の16進文字列（`Guid`の`N`形式） |
| `Operation` | 必須 | 操作を表す識別子。`LogEventDefinition.md`に定義する |
| `Event` | 必須 | 操作中に発生したイベント。`LogEventDefinition.md`に定義する |
| `Outcome` | 条件付き | 検証結果や失敗結果を区別するコードが存在する場合に記録 |
| 補足項目 | 任意 | 保存種別、遷移前後の状態等、イベント定義で指定した情報 |

同一起動セッションの`SessionId`は変化しない。PerformanceLoggerに渡す`SessionId`と共通化し、異なる起動セッションでは別のIDを用いる。

1イベントは1ログレコードとして扱う。`Operation`、`Event`、補足項目に含まれるバックスラッシュは`\\`、CRは`\r`、LFは`\n`にエスケープし、ログを複数行に分断しない。補足項目が`null`または空文字列なら末尾に余分な空白を追加しない。

### 4.3 例外情報

予期しない例外は、例外の型、メッセージおよびスタックトレースを追跡できる形で記録する。内部例外がある場合はその情報も対象とする。

例外の文字列化には`Exception.ToString()`相当の情報を用い、改行をエスケープする。例外の文字列化に失敗した場合は、取得可能な例外型等へフォールバックする。例外情報の生成や整形に失敗しても、本来のエラー通知を妨げない。

### 4.4 記録しない情報

以下を診断ログに無条件で出力しない。

- 御魂の全入力値、式神ステータス一式、保存データJSON全文
- パスワード、認証情報、環境変数の一括出力
- 頻繁に発生するComboBox・TextBox等のControlイベント
- 性能計測の生データ（PerformanceTracker側で管理する）

ファイルの識別が必要な場合、保存種別やファイル名など必要最小限の情報を記録する。ファイルパス全量は、障害調査上必要な場合に限定する。

## 5. 実装上の責務と保存先

### 5.1 Logger

`Gui.Logging.Logger`は、診断イベントのレベル・Operation・Event・補足項目を受け取り、日時とSessionIdを付加して1レコードに整形する。

公開APIは以下を基本とする。

```csharp
Logger.Info(string operation, string eventName, string details = null);
Logger.Warning(string operation, string eventName, string details = null);
Logger.Error(string operation, string eventName, string details = null);
Logger.Error(string operation, string eventName, Exception exception, string details = null);
```

旧形式のメッセージ文字列のみを受け取るAPIは使用しない。`Operation=...`や`Event=...`を文字列全体で組み立てて単一引数に渡す形式も使用しない。

`Logger.SessionId`は同一起動セッション内で不変とする。`Logger`はファイル追記処理を直接実行せず、`LogWriter`に委譲する。診断ログの書き込み失敗は呼び出し元に伝播しない。

### 5.2 LogWriter

`Gui.Logging.LogWriter`は、レコードのファイル出力、同一インスタンス内での排他制御、および書き込み失敗の吸収を担当する。

`TryWrite(string logLine)`は書き込み成功時に`true`、失敗時に`false`を返す。書き込みのために発生した例外を呼び出し元へ伝播しない。失敗したレコードを自動的に再試行せず、次回の書き込み要求は独立して処理する。

書き込み処理の注入は、ファイルI/Oを伴わないテストで成功・失敗を再現するために使用できる。出力方式を変更する場合も、Loggerのイベント形式と利用側の契約は維持する。

### 5.3 保存先・ファイル管理

診断ログは既存の`Log`ディレクトリに日付ごとに追記する。

```text
Log/ShikigamiApp_yyyyMMdd.log
```

同じ日に複数回起動した場合は同じファイルに追記し、`SessionId`で区別する。既存ファイルの内容を上書きしない。文字コードはUTF-8とする。ログディレクトリが存在しなければ、書き込み時に作成を試みる。

PerformanceTrackerの集計ログは従来どおり別ファイルで管理する。

```text
Log/ShikigamiApp_Performance_yyyyMMdd.log
```

日時によるログファイルの切り替えは書き込み時点のローカル日付に従う。同一ファイルに対する別プロセスからの同時書き込み成功までは保証しない。

## 6. 記録タイミングと順序

### 6.1 操作の境界

- 操作が実際に開始される時点で`Started`を記録する。ダイアログをキャンセルした場合など、操作を開始していない場合は記録しない。
- 操作の成功条件を満たした時点で`Completed`を記録する。
- 操作が失敗した場合、失敗が確定した処理境界で`Failed`または専用の失敗イベントを記録する。
- 入力検証で処理を実行できない場合は`ValidationRejected`を記録し、`Completed`は出さない。
- 一度の操作に対し、成功・失敗の終端イベントを重複させない。例外からの復旧処理は元の操作とは区別して記録する。

各イベントの正確な発生条件は`LogEventDefinition.md`に定義する。

### 6.2 イベントの意味

`Completed`はそのイベントで定義した対象処理の正常終了を示す。例えば`SaveData.Load.Completed`はファイル読み取りだけでなく、読み込んだデータの検証とGuiへの適用が完了したことを意味する。

ログが存在しないことだけを根拠に処理失敗を断定してはならない。書き込み障害や異常終了によりイベントが保存されない場合がある。

### 6.3 順序

同一スレッドが逐次発行した書き込みは発行順を維持する。同一`LogWriter`に対する複数スレッドの書き込みは排他制御によって直列化され、ロックを取得した順に記録する。別スレッド間の呼び出し開始順を厳密に保証するものではない。

イベント日時はLoggerで整形した時点の値であり、スレッドの競合によりログへの追記順と一致しない場合がある。書き込み順と発生時刻の違いによってイベントの意味が変わらないようにする。

## 7. ログ出力障害時の動作

1. ログのファイル書き込みやディレクトリへのアクセスに失敗しても、Loggerを呼び出した操作にログ由来の例外を伝播させない。
2. ログ出力の失敗を、同じLoggerへの再帰呼び出しで記録しない。
3. 書き込みに失敗しても、ユーザー向けの警告・エラーダイアログ表示を継続する。
4. 操作状態の変更・保存ボタンの有効状態更新・例外時の状態復帰を、ログ書き込みの成否に依存させない。
5. 本来の保存や読み込みで発生した例外と、ログ出力失敗は区別する。ログ失敗により元の例外を置き換えない。
6. ログ出力が不可能な環境では、該当イベントが永続化されないことを許容する。ただし、アプリケーション操作を妨げない。

この節は外部から見える動作保証であり、書き込み処理の同期・非同期化や内部バッファの有無を呼び出し元の契約としない。

## 8. 終了処理

正常終了時は、終了過程を表すイベントを可能な限り保存先へ反映し、ログの書き込み失敗で終了を妨げない。

終了処理の詳細チェックポイントは`LogEventDefinition.md`に定義する。`Closing`と`Closed`は別の完了地点を表し、フォーム終了がキャンセルされた場合に`Closed`を記録しない。

強制終了、プロセス異常終了、OS停止などでは、一部のイベントが保存されない可能性がある。異常終了時の全件永続化は保証しない。

## 9. PerformanceTrackerとの関係

- Loggerは「どの操作がどこまで進行し、どのような結果になったか」を扱う。
- PerformanceTrackerは「処理にどの程度の時間がかかったか」を扱う。
- 両者は同じ`SessionId`を使用し、調査時に相関させられるようにする。
- LoggerからPerformanceTrackerへ計測値の書き込みを再帰的に呼び出さない。
- PerformanceLogger自体の出力失敗は`PerformanceLog.Failed`として診断ログに記録するが、性能計測値はLoggerに複製しない。

## 10. テスト要件

### 10.1 Logger / LogWriterの単体テスト

- 日時形式、レベル、SessionId、Operation、Event、補足項目が正しく整形されること。
- 同じ起動セッションでSessionIdが一致し、32桁の16進文字列になること。
- 文字列内の改行とバックスラッシュをエスケープし、1イベントが1レコードとなること。
- 補足項目が未指定でも不要な空白を出力しないこと。
- 例外の型・メッセージ・内部例外等を追跡できること。
- ファイル書き込みが成功すれば追記され、以前のデータを上書きしないこと。
- 書き込み失敗時に`false`を返し、例外を伝播せず、自動再試行をしないこと。次回の書き込みは成功可能であること。
- 同一`LogWriter`の書き込みが並行呼び出しによって重ならず、逐次呼び出し順が維持されること。

### 10.2 操作側との結合テスト

- 同一操作で`Started`と`Completed`が適切に対応すること。未完了の処理を`Completed`としないこと。
- 検証失敗・例外・ロールバック成功・ロールバック失敗が正しく区別されること。
- ログ出力失敗時でも、ユーザー通知と操作状態の復帰が実行されること。
- 同一障害に対する不要な重複`ERROR`がないこと。
- ダイアログのキャンセルや単純な入力変更によって大量のログが発生しないこと。
- 別プロセス起動で異なるSessionIdが付与されること。

単体テストの成功だけで、操作側の正常系・異常系ログの網羅を完了扱いにしない。
