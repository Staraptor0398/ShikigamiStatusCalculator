# ShikigamiApp ログ仕様

## 1. 目的

本書は、ShikigamiAppのGuiが出力する診断ログについて、記録内容、出力形式、保存先、出力時の動作、および障害時の取り扱いを定義する。

ログは、異常の発生事実だけでなく、操作開始から正常終了・失敗までの進行状況を追跡し、最後に正常完了した処理を特定できることを目的とする。

対象はGuiの診断ログであり、ScenarioRunnerの実行ログ、CoreTestのテスト結果ログ、およびPerformanceTrackerの計測値は対象外とする。

## 2. 基本原則

1. ユーザーにとって意味のある操作単位で記録する。個々のControlのイベント発火や御魂スロットの値設定など、細粒度の内部操作は原則として記録しない。
2. 操作の開始、正常完了、失敗を区別する。操作途中の到達地点が障害解析に重要な場合に限り、中間の完了イベントを記録する。
3. 正常完了を示すログは、そのイベントが表す処理の完了を確認してから記録する。処理の呼び出し直後や実行前に成功ログを出してはならない。
4. 診断ログ出力の失敗によって、保存・読み込み・計算・状態遷移・エラー通知等の本来の処理を中断しない。
5. ログから原因を追えるよう、イベント名と結果コードを一貫した形式で記録する。ただし、ログだけで処理が完了したことを保証するものではない。
6. 同一障害を複数の層で重複してError記録することは避け、利用者へ失敗を報告する処理境界で原則1回記録する。

## 3. ログレベル

| レベル | 用途 | 主な対象 |
|---|---|---|
| `INFO` | 操作の開始・正常完了・主要状態変化 | 計算成功、保存成功、読み込み成功、式神復旧成功、状態遷移 |
| `WARNING` | 操作を継続できる入力不正、想定された拒否、復旧可能な事象 | Calculation入力検証失敗、式神入力検証失敗 |
| `ERROR` | 操作の失敗、復旧不能な状態、予期しない例外 | SaveData保存失敗、ロールバック失敗、Gateway呼び出し例外 |

想定内の入力不正を`ERROR`として扱わない。正常完了した操作を`WARNING`や`ERROR`として記録しない。

## 4. 出力形式

### 4.1 形式

診断ログの各イベントは以下の形式で記録する。

```text
<日時> [<レベル>] SessionId=<ID> Operation=<操作名> Event=<イベント名> [Outcome=<結果>] [補足項目]
```

例：

```text
2026-11-20 12:00:00.100 [INFO] SessionId=0123456789abcdef0123456789abcdef Operation=Calculation Event=Started
2026-11-20 12:00:00.124 [INFO] SessionId=0123456789abcdef0123456789abcdef Operation=Calculation Event=Completed ShikigamiSelected=True
2026-11-20 12:01:15.200 [WARNING] SessionId=0123456789abcdef0123456789abcdef Operation=Calculation Event=ValidationRejected Outcome=INVALID_VALUE
```

上記のID・時刻・イベントは出力例である。

### 4.2 共通項目

| 項目 | 必須 | 仕様 |
|---|---|---|
| 日時 | 必須 | イベントが発生したローカル日時。書式は`yyyy-MM-dd HH:mm:ss.fff` |
| レベル | 必須 | `INFO`、`WARNING`、`ERROR` |
| `SessionId` | 必須 | アプリの起動単位で生成する一意の識別子。32桁の16進文字列 |
| `Operation` | 必須 | 操作を表す識別子。`LogEventDefinition.md`に定義する |
| `Event` | 必須 | 操作中に発生したイベント。`LogEventDefinition.md`に定義する |
| `Outcome` | 条件付き | 検証結果や失敗結果を区別するコードが存在する場合に記録 |
| 補足項目 | 任意 | 保存種別、遷移前後の状態等、イベント定義で指定した情報 |

`SessionId`は同じ起動セッション内で変更せず、PerformanceTrackerのセッション識別子と共通化する。異なる起動セッションは別のIDを使用する。

1イベントは1つのログレコードとして扱う。改行を含むメッセージおよび例外文字列はレコードを分断しない形式へ変換して記録する。

### 4.3 例外情報

予期しない例外を記録するときは、少なくとも例外の型、メッセージおよびスタックトレースを追跡できる情報を記録する。内部例外がある場合はその情報も対象とする。

例外文字列の改行は1レコード内に収まるようエスケープする。例外情報の生成や整形に失敗した場合も、本来のエラー通知を妨げない。

### 4.4 記録しない情報

以下を診断ログに無条件で出力しない。

- 御魂の全入力値、式神ステータス一式、保存データJSON全文
- パスワード、認証情報、環境変数の一括出力
- 頻繁に発生するComboBox・TextBox等のControlイベント
- 性能計測の生データ（PerformanceTracker側で管理する）

ファイルの識別が必要な場合、保存種別やファイル名など必要最小限の情報を記録する。ファイルパスの全量を記録する場合は、障害調査上の必要性を確認する。

## 5. 保存先・ファイル管理

診断ログの保存先は既存の`Log`ディレクトリとし、日付ごとに次のファイルへ追記する。

```text
Log/ShikigamiApp_yyyyMMdd.log
```

同じ日に複数回起動した場合は同じファイルに追記し、`SessionId`で区別する。既存ファイルの内容を上書きしない。文字コードはUTF-8とする。

PerformanceTrackerの集計ログは従来どおり別ファイルで管理する。

```text
Log/ShikigamiApp_Performance_yyyyMMdd.log
```

ログ保存処理の内部構成にかかわらず、外部から参照する保存先とレコード形式は本仕様に従う。

## 6. 記録タイミングと順序

### 6.1 操作の境界

- 操作が実際に開始される時点で`Started`を記録する。
- 操作の成功条件を満たした時点で`Completed`を記録する。
- 操作が失敗した場合、失敗が確定した処理境界で`Failed`または専用の失敗イベントを記録する。
- 入力検証で操作を開始できない場合は`ValidationRejected`を記録する。検証失敗後に`Completed`を出力してはならない。
- 一度の操作に対し、成功・失敗の終端イベントを重複させない。例外からの復旧処理は元の操作とは区別して記録する。

各イベントの正確な発生条件は`LogEventDefinition.md`に定義する。

### 6.2 イベントの意味

`Completed`はそのイベントで定義した対象処理の正常終了を示す。例として、`SaveData.Load`の完了はファイル読み取りだけでなく、読み込んだデータの検証とGuiへの適用の完了を意味する。

ログが存在しないことだけを根拠に処理失敗を断定してはならない。ログ出力障害や異常終了によってイベントが記録されない可能性がある。

### 6.3 順序

同一の実行スレッドから発生したイベントの順序を保つ。複数スレッドから記録する場合も、Loggerが受け付けた順序を維持する。

ログの順序と発生時刻に不一致があり得る場合でも、イベントの意味が変わらないようにする。

## 7. ログ出力障害時の動作

1. ログのファイル書き込み、ディレクトリへのアクセス等で障害が発生しても、Loggerを呼び出した操作にログ由来の例外を伝播させない。
2. ログ出力に失敗したことを、同じLoggerへの再帰呼び出しで記録しない。
3. ログが失敗しても、ユーザー向けの警告・エラーダイアログ表示を継続する。
4. 操作状態の変更・保存ボタンの有効状態更新・例外時の状態復帰を、ログ書き込みの成否に依存させない。
5. 本来の保存や読み込みで発生した例外と、ログ出力の失敗は区別する。ログ失敗によって元の例外情報を置き換えない。
6. ログ出力が不可能な環境では、該当イベントが永続化されないことは許容する。ただし、この障害によりアプリケーション操作を妨げてはならない。

この節は外部から見えるLoggerの動作保証を定義する。書き込み処理の同期・非同期化や内部バッファの有無は、呼び出し元が依存する契約としない。

## 8. 終了処理

正常終了時は、記録対象となったイベントを可能な限り保存先へ反映し、終了処理自体をログの書き込み失敗で妨げない。

強制終了、プロセス異常終了、OS停止などでは、一部のイベントがファイルへ反映されない可能性がある。異常終了時の全件永続化は保証しない。

## 9. PerformanceTrackerとの関係

- Loggerは「どの操作がどこまで進行し、どのような結果になったか」を扱う。
- PerformanceTrackerは「処理にどの程度の時間がかかったか」を扱う。
- 両者は同じ`SessionId`を使用し、調査時に相関させられるようにする。
- LoggerからPerformanceTrackerへ書き込み処理を再帰的に呼び出さない。

## 10. テスト要件

- 指定された日時形式、レベル、SessionId、Operation、Eventが出力されること。
- 同じ起動セッションでSessionIdが一致し、別セッションでは異なること。
- 正常完了していない操作に`Completed`を記録しないこと。
- ログ出力におけるI/O例外が、通常の操作とエラー通知を中断させないこと。
- ログ出力失敗時でも操作状態が適切に復帰すること。
- 同一操作中に意図しない重複`ERROR`が出力されないこと。
- 一つのイベントメッセージに改行を含んでもログレコードとして分断されないこと。
- 複数の操作が同日に実行されても既存のログを上書きしないこと。
